## 3. 各层写入边界

| 目录 | 应当放入 | 不应放入 |
|---|---|---|
| `frontend/` | 页面、交互、前端状态、格式展示 | 独立收益计算、直接访问行情供应商、供应商密钥 |
| `api/` | 输入输出转换、访问控制入口 | 再实现一套策略、账户或费用规则 |
| `application/` | 数据入库、研究更新、账户导入等用例及跨域协调 | 供应商 SDK 细节、UI 代码 |
| `domain/` | 可复现计算、业务约束、状态转换 | HTTP 客户端、数据库连接、框架启动代码 |
| `ports/` | 业务所需外部能力的抽象接口 | 第三方专属对象、具体连接配置 |
| `adapters/` | 第三方对象转换、外部错误映射、接入实现 | 绕过权限或直接修改账本的捷径 |
| `infrastructure/` | 仓储实现、缓存、任务运行状态存储 | 另一套买卖决策规则 |
| `jobs/` | 调用应用用例、重试、检查点、任务状态更新 | 与 API 入口不同的费用或计算逻辑 |
| `contracts/` | 对外接口、事件与生成约定 | 密钥、真实账户数据、重复手工维护的前端类型 |

## 4. 依赖方向

```text
frontend ──公开契约──> api ──> application ──> domain
jobs ──────────────────────> application
application ──> ports
adapters / infrastructure ──实现──> ports
bootstrap ──装配──> 上述入口和具体实现
```

领域核心不依赖前端、供应商或数据库实现。模块间协调放在 `application/`，通过明确接口和数据对象交互，不跨模块写数据库表。业务模块不能通过 `shared/` 间接形成循环依赖。

公开契约需要在技术定案时确定唯一生成来源：若由后端生成，则禁止手工修改生成文件；若契约先行，则后端实现与客户端通过契约检查约束，不能同时维护两份“权威定义”。

## 5. 运行与数据目录

第一阶段允许同一代码包启动一个 API 进程和一个后台 worker，二者共享应用用例与领域规则。是否需要独立调度进程、消息队列或更多服务，留到实际容量与故障需求明确后决定。

数据文件、缓存、导入账户资料、任务日志和生成报告放到**仓库外的可配置运行目录**。本次不设置实际存储路径、不创建数据库。后续引入配置时同步维护 `.gitignore` 和无真实凭据的配置样例；真实密钥与个人持仓不得提交。

测试约定区分两类：正式维护的测试放在 `tests/` 或选定框架规定的相邻位置，两者选择一种并形成决策记录；一次性验证资产统一放在 `D:\test\pstock\<任务>\`。

## 6. 与开源组件的关系

开源项目的名称可以出现在 `adapters/` 内的具体实现或 `readme/integrations/` 接入记录中。不要因为参考多个项目就增加多套首页、账户、数据仓库和调度系统。

如果最终选择基于 TSP 改造，先固定提交并梳理原目录到本结构的映射，再分批迁移；不要先大规模搬文件导致候选底座无法启动。若选择自建主应用，则按本结构逐步创建模块。当前规划保留两条路线，不代表已经选择 fork 或引入源码。
