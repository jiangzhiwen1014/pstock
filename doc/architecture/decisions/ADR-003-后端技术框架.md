# ADR-003 后端技术框架

日期：2026-09-10。状态：已采纳技术基线，尚未实现或部署。权威说明见 [后端架构](../后端架构.md)。

## 背景

用户要求按原规划任务的个人投研需求选择后端：消息面、技术面、公司能力、外围影响、持仓决策及持续复盘。前期实时性要求低，后续迭代可能提高实时性。已有持续在线的 4 核 4G 云服务器；用户明确初期使用 PG 或 MySQL 承担存储，暂缓 Redis/RQ。

## 决策

采用 Python + FastAPI 模块化单体，共用业务代码的 API 与后台任务分进程运行。选 PostgreSQL 作为初期唯一数据库，SQLAlchemy + Psycopg 访问，Alembic 管理迁移；Pydantic 管理边界模型。初期同步数据库访问，阻塞工作不得放入异步事件循环。API 一个进程，worker 一个执行槽。

采用数据库持久任务表、短事务领取、租约心跳、有限重试和业务幂等；周期任务由轻量调度循环触发。Redis、RQ、高频订阅、SSE/WebSocket 与多服务拆分在延迟目标和负载证据支持时引入。精确版本、包管理和部署工具在工程初始化/环境核验后确定。

## 备选与选择理由

| 路线 | 判断 |
|---|---|
| Python 主应用和研究任务 | 数据接入、批量研究、回测与日常分析容易共享代码，符合当前需求重心；采用 |
| Java 主应用 + Python 研究任务 | 适合存在明确 Java 维护或业务集成优势时；当前增加跨语言契约与部署成本，未采用 |
| 多个完整开源系统组合运行 | 容易形成多套账户、数据和计算口径，未采用；按模块选择性复用 |
| MySQL | 可作为替代，但当前选 PG 并只验证一种数据库；SQLAlchemy 不保证数据库切换透明 |
| 初期 Redis + RQ | 增加运行组件，不符合用户当前资源策略；保留为后续候选 |

## 代价、演进与回退

自行维护数据库任务机制需要完成领取、失联恢复、幂等和通知副作用验证；单执行槽可能造成积压，长任务必须分批。Python 不保证更快或更省内存，4G 机器容量需实测。

提高实时性时，按来源和功能逐步引入订阅与增量计算，保持批量回补能力；新调度分发机制切换前停止旧分发或提供明确唯一所有者，迁移未完成任务并核对执行状态，避免双重消费。保留业务幂等键和任务追踪。若切换失败，暂停新分发、核对租约与已执行效果后恢复数据库分发，不能直接并行启用两套调度。

数据库结构优先采用兼容的增量迁移；程序回退需匹配数据库兼容窗口。破坏性迁移通过已验证备份恢复或前向修复，不承诺无损自动降级。
